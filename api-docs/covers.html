Covers

How the Cover Store builds thumbnail URLs, which sizes to serve, and when a static source can skip hosting images altogether.

URL template

By default, the Cover Store builds every thumbnail URL as:

{coversUrl}/{mangaId}/{coverFile}.{size}.jpg
  • {coversUrl} — from _meta.json, or {baseUrl}/covers if the key is absent.
  • {mangaId} — the manga's id as served by the API.
  • {coverFile} — the stem of the file name on the cover-art relationship. The demo uses the literal string cover, so files are cover.256.jpg; a real source may use hashed names like abc123de-f456.jpg, in which case {coverFile} would be abc123de-f456.jpg.
  • {size} — the current thumbnail width in pixels (see below).

Sizes

Two sizes are expected to exist for every cover:

  • .256.jpg — tile size, used on Home, Browse, Library, Search, and anywhere a cover is rendered under ~128pt on screen.
  • .512.jpg — larger size, used on the title detail header.

If a size file is missing (404), the tile stays as a grey placeholder; the app does not downscale a larger file at the client. A source that only serves one size should serve the larger one at both paths (symlink or copy).

Example

For a title with id = "demo-01" and the covers CDN at https://lajennylove.github.io/readex/covers, the two URLs are:

https://lajennylove.github.io/readex/covers/demo-01/cover.256.jpg
https://lajennylove.github.io/readex/covers/demo-01/cover.512.jpg

Formats

The URL template is hard-coded to the .jpg suffix. Serving a PNG or WebP at that path works (the client validates the body with its image decoder, not the extension), but the request path will still end in .jpg — the CDN must therefore respond at that path regardless of the actual bytes' MIME type.

If your backend only produces PNG, point the cover_art relationship's fileName at an absolute URL instead (see below).

Short-circuit: absolute URLs in the API response

When a manga's cover_art relationship has an attributes.fileName starting with http:// or https://, the Cover Store skips the template entirely and uses that URL verbatim. The demo relies on this to serve placehold.co images without hosting any JPEG files for the primary catalog.

"relationships": [
  { "id": "cover-demo-01", "type": "cover_art",
    "attributes": { "fileName": "https://placehold.co/400x600/1a1a2e/eeeeee.png?text=Lorem+Ipsum+Dolor" } }
]

With absolute URLs the {size} suffix convention does not apply — the server returns whatever bytes live at that URL, and the client scales for display.

Downloads & caching

Thumbnails live in the OS cache tier (<caches>/covers/{mangaId}/…) and can be purged by iOS without warning. The app re-downloads on miss. The CDN should allow long-lived caching headers (Cache-Control: public, max-age=…); content-rated catalogs may need signed URLs, in which case the _meta.json covers_url can point at a signing proxy.

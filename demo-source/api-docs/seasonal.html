Seasonal

The optional "This season" row contract.

What this is

The Home screen has an optional top row named This season. It is populated from a single JSON file served at a URL the user pastes into Settings. The URL is per-install: it does not have to live on the same host as the API, and it has no default location. If the user doesn't opt in, the row is hidden and no outbound call is made.

Everything else on Home works whether or not this row exists. Treat it as entirely optional.

Response schema

A single JSON object with three top-level keys:

{
  "id":        "string, stable identifier for the list",
  "name":      "string, display name shown as the row heading",
  "manga_ids": ["array of manga.id strings served by the current source"]
}

No envelope. No result/response wrapper. No pagination. The manga_ids are used as-is to request each title's detail via /manga/{id}; IDs that 404 are dropped silently.

Minimal example

{
  "id": "demo-seasonal-2026-fall",
  "name": "Fall 2026 picks",
  "manga_ids": [
    "demo-01",
    "demo-03",
    "demo-07"
  ]
}

Hosting notes

  • Served over HTTPS. Any JSON content type is accepted.
  • Order is preserved — the client renders tiles in the order the IDs appear.
  • There is no cross-reference back to the API; the client assumes every ID resolves at the active source. If the list is maintained independently (e.g. a community curator), stale IDs are tolerated but not helpful.
  • No cache headers are read; the client refreshes the row on the normal Home refresh cadence.

Not to be confused with /api/manga/_seasonal.json

The demo also ships a file at /api/manga/_seasonal.json that uses the standard collection envelope with a list of IDs under data. This is a legacy path from an earlier version of the contract and is not what the "This season" setting fetches today. New sources should implement only the {id, name, manga_ids} shape described above.
